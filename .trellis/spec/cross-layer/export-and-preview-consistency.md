# Export And Preview Consistency

The preview should approximate Word output closely enough for users to trust it. It does not need to be a perfect DOCX renderer, but supported Markdown and style controls should not drift without an explicit reason. The current preview path renders a temporary DOCX generated by the Python backend; do not reintroduce a separate front-end Markdown DOM preview without a new product decision.

## Scenario: Adding Or Changing Exported Markdown Behavior

### 1. Scope / Trigger

This applies when changing Markdown syntax support, preview rendering, DOCX rendering, export temp-file handling, or user-visible export errors.

### 2. Signatures

- Preview renderer: `Preview({ markdown, cfg })` in `src/components/preview/Preview.tsx`, backed by `useExportPreview` and `DocxRenderPreview`
- Export hook: `useExport({ content, cfg, showToast })` in `src/features/export/useExport.ts`
- Sidecar call: `exportWithPython(options: ExportOptions)` in `src/features/export/pythonBackend.ts`
- Backend CLI: `backend/backend.py --input --output --config-file`
- Backend converter: `convert(input_path, output_path, conf)` in `backend/converter.py`

### 3. Contracts

- `ExportOptions.markdown`: non-empty Markdown string
- `ExportOptions.outputPath`: user-selected `.docx` path
- `ExportOptions.config`: serialized `DocumentConfig`
- Backend stdout/stderr and exit code are interpreted by `pythonBackend.ts`
- Temporary Markdown and config files live in Tauri `BaseDirectory.AppCache` and are removed in `finally`

### 4. Validation & Error Matrix

- Empty Markdown -> front-end returns `success: false` with `内容为空`
- Missing output path -> front-end returns `success: false` with `输出路径无效`
- Backend exit code 1 -> file-not-found message
- Backend exit code 2 + locked-file markers -> `无法写入目标文件`
- Backend exit code 3 -> config error message
- Backend exit code 4 -> Markdown parse failure message
- Backend exit code 5 -> DOCX generation failure message
- Invalid UTF-8 error from shell plugin -> neutral export failure with likely file-lock hint

### 5. Good / Base / Bad Cases

- Good: Add support for a Markdown construct in the backend conversion path, then verify the DOCX preview and exported DOCX both show it.
- Base: Add DOCX-preview shell behavior, such as renderer sizing or link safety, without changing Markdown conversion semantics.
- Bad: Add a second front-end Markdown-to-layout implementation that can drift from backend DOCX export.

### 6. Tests Required

- Preview status/render behavior: `test/components/preview/Preview.test.tsx` and `test/components/preview/DocxRenderPreview.test.tsx`
- Export error mapping: `test/features/export/pythonBackend.test.ts`
- Backend DOCX output: targeted tests under `backend/tests/`

### 7. Wrong vs Correct

Wrong: Add a new front-end-only Markdown renderer branch and assume export works.

Correct: trace preview, config, backend parser/converter, DOCX styling, and tests before calling the behavior supported.

## Shared Behaviors

Keep these backend-export and DOCX-preview behaviors aligned:

- Headings: first H1 can become document title when `bodyStart.firstHeadingAsTitle` is enabled.
- Body paragraphs: body style, first-line indent, line spacing, margins.
- Code: inline code and fenced code use code style and background.
- Quotes: quote style and left indent.
- Horizontal rules: `default`, `page_break`, and `hidden`.
- Tables: GFM tables, header background, cell borders, alignments, `tableHeaderBold`.
- Captions: lines starting with `图`, `表`, or `公式` auto-number in backend and appear through the generated DOCX preview.
- Underline: front-end inline formatting produces `<u>`, backend parser converts `<u>` to underlined runs, and the DOCX renderer displays the generated output.

Reference files:
- `src/components/preview/Preview.tsx`
- `src/components/preview/DocxRenderPreview.tsx`
- `src/features/preview/useExportPreview.ts`
- `backend/converter.py`
- `backend/parser.py`

- `backend/converters/table.py`

## When Adding Markdown Support

For a new Markdown construct:

1. Decide whether it is preview-only or export-supported.
2. If export-supported, add backend parsing/rendering and tests.
3. Verify the generated DOCX preview reflects the backend output; do not add a front-end Markdown-only rendering path.
4. Add tests for preview status/renderer behavior and DOCX output.
5. Update user-facing controls only after the conversion path exists.

Do not add preview support that implies export support unless the backend can actually render it.

## Export Flow

`src/features/export/useExport.ts` chooses a default filename from the first H1, opens a Tauri save dialog, then calls `exportWithPython`.

`src/features/export/pythonBackend.ts`:

- writes Markdown to `BaseDirectory.AppCache`
- writes config JSON to `BaseDirectory.AppCache`
- executes sidecar `binaries/md2word`
- maps backend exit codes to user-facing errors
- removes temp files in `finally`

`backend/backend.py` accepts `--input`, `--output`, and `--config-file`, then calls `convert`.

Do not bypass this flow from UI components.

## Scenario: Export-Grade Paged Preview Via DOCX Renderer

### 1. Scope / Trigger

This applies when changing the export-grade preview path that spans React preview UI, Tauri AppCache temp files, sidecar execution, and browser DOCX rendering.

### 2. Signatures

- Preview generator: `generateExportPreviewDocx({ markdown, config })`
- Preview hook: `useExportPreview({ markdown, cfg, enabled?, debounceMs? })`
- Renderer component: `DocxRenderPreview({ docxBytes, onRenderError?, onPageCountChange? })`
- Sidecar command: `binaries/md2word --input <md-path> --output <docx-path> --config-file <json-path>`
- Renderer package: `docx-renderer@0.2.0` with `render(data, bodyContainer, styleContainer, { breakPages: true })`

### 3. Contracts

- `markdown`: non-empty Markdown string; empty content returns a structured preview error before sidecar execution.
- `config`: current `DocumentConfig`, serialized to a temporary JSON file in `BaseDirectory.AppCache`.
- Temporary output: a generated `.docx` path in `BaseDirectory.AppCache`; no user save dialog and no PDF output.
- `generateExportPreviewDocx` returns `{ success: true, docxBytes }` after reading the generated DOCX bytes, then removes temporary Markdown/config/DOCX files in `finally`.
- `useExportPreview` keeps the previous successful `docxBytes` while a refresh is loading or fails, so the preview does not flash empty.
- `DocxRenderPreview` dynamically imports `docx-renderer`, renders each incoming DOCX into staged body/style containers, swaps the staged DOM into view only after render succeeds, calls `RenderResult.dispose()` during cleanup, reports page count, and confirms before opening external links.
- When a later DOCX render fails after a prior successful render, the staged DOM is discarded and the previous successful DOCX DOM remains visible. The preview may show an error banner, but it must not clear the visible DOCX preview or fall back to Markdown DOM rendering.

### 4. Validation & Error Matrix

- Empty Markdown -> hook remains idle and `Preview.tsx` displays the empty export-preview prompt.
- Sidecar non-zero exit -> `parseBackendError(stderr, code)` result shown in preview status.
- DOCX read failure -> `预览生成不可用`, with details from the filesystem error.
- `docx-renderer` import/render failure -> `Preview.tsx` displays export-preview error details; if a previous DOCX preview is still valid, continue showing it from the existing DOCX DOM.
- Ordinary export remains unchanged: user-selected DOCX export still calls `exportWithPython`, not the preview hook.

### 5. Good / Base / Bad Cases

- Good: Generate a temporary DOCX through the same sidecar args as ordinary export, read bytes from AppCache, render with `docx-renderer`, and preserve the previous DOCX preview while refreshing.
- Base: Add a renderer UI improvement inside `DocxRenderPreview` without changing sidecar arguments or backend CLI behavior.
- Bad: Add `--preview-pdf`, Word COM, LibreOffice, or a second Markdown-to-layout implementation for preview when the accepted route is DOCX renderer.

### 6. Tests Required

- `test/features/export/pythonBackend.test.ts`: assert preview generation uses normal sidecar args, reads the `.docx`, and does not pass `--preview-pdf`.
- `test/features/preview/useExportPreview.test.tsx`: assert debounce, ready state, and previous `docxBytes` retention on refresh failure.
- `test/components/preview/DocxRenderPreview.test.tsx`: mock `docx-renderer.render`, assert `{ breakPages: true }`, `dispose()` on unmount, page-count reporting, external-link confirmation, and previous DOM retention when a refresh render fails.
- `test/components/preview/Preview.test.tsx`: assert loading/error/ready states, render-error status reporting, and that Markdown DOM fallback is not rendered.
- `pnpm run build`: verify Vite can bundle the dynamic `docx-renderer` import.

### 7. Wrong vs Correct

Wrong:

```typescript
Command.sidecar('binaries/md2word', [
  '--input', inputPath,
  '--output', docxPath,
  '--config-file', configPath,
  '--preview-pdf', pdfPath,
]);
```

Correct:

```typescript
Command.sidecar('binaries/md2word', [
  '--input', inputPath,
  '--output', docxPath,
  '--config-file', configPath,
]);
```

Then pass the generated DOCX bytes to `docx-renderer` in the preview layer.

## Known Limitations

The backend line scanner supports a practical subset of Markdown. It does not currently model arbitrary nested block structures. When documenting or adding features, be clear whether the limitation is in preview, backend export, or both.
