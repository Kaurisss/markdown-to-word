  • 导航成本下降——7 个 150 行文件 vs 1 个 1084 行文件

5. 把 hook-per-instance store 深化为真正的 singleton store

Speculative

Files

src/services/aiConfigStore.ts (154 行)
src/services/settingsStore.ts (134 行)

Before

useAIConfigStore()

每个调用方创建独立 useState

通过 StorageEvent 跨实例同步

full JSON parse/serialize on every sync

App 实例

Header 实例

AITab 实例

3 copies of state, synced via events

After

Zustand / useSyncExternalStore

单一 store 实例

subscribe 触发精确 re-render

App ←subscribe

Header ←subscribe

AITab ←subscribe

1 source of truth, N subscribers

Problem: useAIConfigStore 和 useSettingsStore 使用 useState + StorageEvent 模拟全局 store。每个调用方各持一份状态副本，通过 JSON serialize/parse 同步。同一窗口内多个调用方出现状态短暂不一致（race condition），且每次 storage event 触发 full re-parse。

Solution: 用 useSyncExternalStore（React 内置）或 Zustand 替换，实现真正的单例 store。跨窗口同步逻辑保持 StorageEvent 但只在 store 层面处理一次。

Wins

  • Locality: 状态变更集中在 store module，不再每个 hook 实例各自同步
  • 消除 race condition（单一 source of truth）
  • 减少不必要的 JSON parse/serialize

⚠️ 标记为 Speculative：当前的 StorageEvent 同步在跨 Tauri WebviewWindow 的场景下工作正常，引入外部依赖（Zustand）需要权衡。如果只在单窗口内使用，用 React Context 或 useSyncExternalStore 就够了，无需新依赖。

🏆 首先处理: 合并 AIConfig 的两个 near-clone modules (#2)

这是回报最高且风险最低的 deepening。两个文件有 ~90% 代码重复，已经存在两个真实 adapter（Modal 和 Window），证明 seam 是真实的而非 hypothetical。抽取 useAIConfig hook 预计可以删除 ~700 行代码，并且由于 interface 已经是现成的（两个 adapter 消费的交集），提取过程几乎是机械性的。完成后自然暴露出 #1（App.tsx 拆解）的路径——因为 AI 配置的状态管理不再需要在 App 中 passthrough。
